# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

Implemented so far: the `macro/` minimal loop (schema, runner, executor, recorder, act, vision/fingerprint, anchors, screenshot storage, audit incl. reviewer/reporter) + platform pack export / import (`adapters/pack.py`, `.cwpack`) + `infra/sqlite` audit store + `studio/` (macro editor at `/`, audit page at `/audit`) + CLI `studio` / `record` / `anchor` / `run`. Everything else in the README tree is still to be built, in roadmap order. Usage: `docs/studio.md`, `docs/macro.md`. **`README.zh-CN.md` is the source of truth**; `README.md` is its English translation. When the design changes, update the Chinese README first, then sync the English one and this file. The "目录结构 / Project structure" section is the target layout, so build toward it rather than inventing a different structure.

## Commands

```bash
uv sync                                   # install dependencies (Python 3.11+)
uv run cyber-worker studio                # web editor + audit page on :9999 (macOS / Windows)
uv run cyber-worker record OUT.yaml --app WeChat --size 1200x900
uv run cyber-worker anchor SCRIPT.yaml PAGE --region x,y,w,h
uv run cyber-worker run SCRIPT.yaml [--dry-run] [--var name=value]
uv run pytest                             # run tests
uv run pytest tests/macro/test_runner.py::test_name   # single test
```

Supported platforms are **macOS and Windows** (`bootstrap._platform_io` picks one; Linux raises). Shared mouse/keyboard code lives in `macro/io/pynput_input.py`. `macos.py` handles windows and capture via `screencapture` + `osascript`. `windows.py` uses Win32 via ctypes + Pillow. `capture` uses `PrintWindow(PW_RENDERFULLCONTENT)` on `WindowGeometry.handle` (the window's own pixels, correct even when another window covers it), cropped to the DWM frame; it falls back to a screen grab when there is no handle, the result is all black, or the size is off. A covered window captured as a screen region once produced a bogus hover whose step image showed the studio page. A window that is gone / minimized / hidden (`_window_gone`) raises CalibrationError instead of falling back (a chat closed with ✕ mid-recording once got the studio page as its reference); the runner's after-step screenshot tolerates that (`_after_shot`). `find_window(app, title=None, size=, avoid=)`: without a title it no longer takes the topmost window of the app but `base.pick_window` (drop titles of the macro's other windows, `Script.other_titles`, then closest size), so a 580-wide chat on top is not mistaken for the 320-wide QQ main window; `calibrate` / `locate_window` take `avoid`. New macros record a fixed title (`window_json.match_title`) unless it looks like `文档 - 程序` and the app has only one window. It is per-monitor DPI aware, so pynput coordinates are physical pixels and `input_factor` converts them to points. It types with `SendInput(KEYEVENTF_UNICODE)` so the Chinese IME can't swallow letters, and uses an Alt-press + `AttachThreadInput` trick to get past foreground-lock. `Window.title` (optional) picks one window when an app has several. Everything else depends on the `ScreenIO` / `ActivityMonitor` protocols in `macro/io/base.py`, and the tests use `tests/fakes.py` (FakeIO records calls; `typed()` replays backspaces and `clear`). `tests/helpers.py` builds synthetic page fingerprints. Test files import `fakes` / `helpers` as top-level modules (via `tests/conftest.py`), so don't add `__init__.py` under `tests/`.

## Architecture

Code lives under `src/cyber_worker/`. **Dependency direction:** `engine` depends only on `engine/ports/`; `adapters` and `infra` implement those ports; `macro` is platform-agnostic; `bootstrap.py` is the single wiring point, called by both `cli.py` and studio. Don't construct dependencies anywhere else.

- **engine/** decides *what*. Ports: `PlatformPort` (watch / extract / browse_feed / like / comment / publish), `ReviewQueue`, `MemoryStore`, `LLM`, `Clock` (fake clock to fast-forward 24h in tests). `monitor.py` polls watch regions; `decision/` holds rule-based policies; `tone/` drafts with the LLM and learns from feedback; `workflow/` holds the long-running state machines.
- **macro/** decides *how*. `executor.py` is the **only** path to the mouse and keyboard: every action (studio recording/runs, engine actions) is queued and mutually exclusive, pauses on user input, and a panic hotkey clears the queue. `runner.py` calibrates the window (coordinates are window-relative, with recorded window size and Retina scale), verifies `expected_page` fingerprints **before any type/send step**. It polls up to `PAGE_WAIT` (5 s) for the page to appear and only then aborts, flagging the action as suspicious. It finds `Click.target` images before clicking (`locator/icon.locate_click`, via `vision/template.find_all`; the nearest match wins). A target can carry a second look, `Target.alt`: the click target is cropped at mouse press, so a button often has its pressed/hover colour (the QQ 「关闭」 button scored only 0.78 in its normal state against a 0.8 threshold). At record stop, `routes/record._normal_look` crops the same box from an earlier frame of that window where the pointer wasn't on it (`vision/template.look_of`: same → no alt; other → alt; different content → skip). `locate_click` takes a list of refs and keeps the best. Runs keep targets fresh by themselves (the user wants no manual 「update」 button): when a target is found with `threshold ≤ score < LEARN_BELOW` (0.9), only one match in the window, and the step succeeded, `Runner._learn` crops it from the find frame and `anchors.learn_look` stores it as `alt` (re-reading the file; the recorded `image` is never touched, `alt` is replaced, not accumulated), and the detail gets `LEARNED_NOTE`. After a run the editor's `pickUpLearnedLooks` reloads the macro (or, with unsaved edits, merges only `alt`) so autosave can't overwrite it. `reviewer.suspicion` marks an ok step whose target score (parsed from the detail `runner._found_text` writes) is below `TARGET_WEAK` (0.85) and wasn't learned as 待看, and the audit page explains it (`weakTarget`: several look-alikes → 重新框选). `relocate_macro`, pack validation and garbage collection cover hover targets and `alt` too (hover target paths used to be left behind on a move). The click offset relative to the target is kept (so a click point dragged off its target clicks off it too: `state.off_target` / editor `offTarget` flag it as a problem; the canvas no longer moves a step on a plain click, only by dragging its marker, because a stray click on the canvas once moved 「关闭」 into the input box and autosave kept it), the runner waits up to `target.timeout` (if the best match is only `NEAR` (≥ 0.6), e.g. a button captured with its hover highlight, it first moves the pointer onto that spot once so the highlight appears, then keeps matching), and if the target never shows it aborts and **never falls back to the old coordinates**. It runs `WaitPage` steps (wait for a page, then continue). It also performs `Click.count == 2` as a real double-click (one move, then two clicks 60–120 ms apart in place; separate click steps are never fast enough for the OS to treat them as a double-click, and the recorder merges clicks at the same spot within 0.5 s into one), clears the input field before typing unless `clear_first: false` (otherwise leftovers from a dry/interrupted run would get sent), screenshots after every step (a step that closes its own window, e.g. clicking 「关闭」, gets the frame from just before the action instead, noted with `CLOSED_NOTE`: the find frame for target clicks, otherwise `_before_shot` for clicks, drags and keys), and supports `dry_run` (everything except the final send). Image algorithms live in `vision/` (ocr, template, fingerprint, detect, anomaly); `locator/` only decides where to click. `audit/` is pure logic, with no HTTP.
- **adapters/** decides *where*, using **declarative platform packs**. One generic `screen_adapter.py` reads each `adapters/<platform>/` pack: `platform.yaml` (capability → macro, extraction regions + OCR, window size), `pages.yaml` (fingerprints, watch regions), `templates/*.yaml` (recorded macros), `reference/`. Adding a platform means adding a pack, not code. Per-platform Python (`hooks.py`) is optional and only for complex extraction. `loader.py` overlays `user_data/platforms/` on top of the built-ins (same-name files win).
- **infra/** holds the concrete port implementations: SQLite (`state.db`: pending queue, memory, audit) and the LLM client (cloud or local).
- **studio/** is FastAPI + WebSocket with a vanilla HTML/JS/Canvas frontend: **web only, no frontend framework, no desktop UI framework** (no Electron/Tauri/PyQt/Tkinter). The editor layout: the subbar has the macro picker on the left and the main actions on the right (`#run-bar`: record ▾, 空跑, 执行); below are three columns: step list (`#steps-card`; the head's 「＋」 `#btn-add` opens `#add-menu` and appends at the end; everything else per step lives in a context menu, right-click a row or its 「⋯」 `[data-more]` (`openStepMenu`: 在后面添加 › / 在前面添加 › / 换成 › / 复制一份 Ctrl+D / 删除 Del, with the type list in `#step-submenu` cloned from `#add-menu`; right-click on blank list space or the empty-macro 「手动添加一步」 → `openEndMenu`, append at the end; both menus live in `index.html` before the scripts); `addStep(kind, at)` puts the new step on the window and frame the canvas is showing (`win` = `S.win`, `shot` = the shown step shot, centre of that window) and pads a 1 s delay on each side whose neighbour isn't already a delay (inserting before a step needs the one after), unless it is itself a delay; 「换成」 (`changeStep`) swaps the step's type in place, keeping id/win/shot/note and carrying over position, `expected_page` and `sends` where the new type has them, undo / redo / delete; tags on a second line under each summary; delays as their own rows) | canvas (`#stage-card`, fills the column; its head row: frame kind 录制画面 / 当前画面 / 运行截图, `#win-seg` labelled with real window names (`windowLabel(null)` is the main window's title, not 「主窗口」), the frame note, and the labelled buttons 「截图」 (`#btn-capture`: always just captures and switches to 当前画面) and 「框锚点」; replacing a recorded frame lives in the 截图 ▾ menu (`#capture-menu`: 「截一张现在的样子」 / 「用现在的样子换掉录制画面」, the latter enabled only on 录制画面), the same split-button pattern as 录制 ▾, because one button silently doing two different things depending on the frame kind confused people; the tour has a step for this row) | panel (`#panel`: 步骤 / 宏设置 / 运行 tabs; field help lives in ⓘ tooltips via `field()`, rarely used fields in a `details.more` fold, 「删除这个宏」 at the bottom of 宏设置). Routes only display and submit; business logic belongs in engine/macro. `studio/state.py` owns all filesystem access (scripts live in `user_data/platforms/<platform>/templates/*.yaml`, path-traversal checked). Worker threads publish to the browser through `Hub.publish` (thread-safe). Every run (dry or real, button, Ctrl+Enter or hotkey) goes through `routes/run.start_run`, which chimes `start` once when it queues the job (unless `[studio] run_chime` is off; recording start/stop chimes follow `[studio] record_chime`; both live in the settings dialog's 「声音」 group next to 操作音效 and are read from `app.config` at each call, so they apply immediately) (the hotkey's hand-off to a dirty page doesn't chime itself, the page's run does). A run publishes `run_state` events in the order `queued` (waiting for the user to stop touching mouse/keyboard), then `running` (published from inside the job), then `done`. The UI must always show what it's waiting for, with a cancel button; never leave a bare disabled button. Events can be lost while the WebSocket reconnects, so the editor re-syncs from `GET /api/status` on reconnect and every 3 s while a run is active. Static files are served `no-cache`. A page left open across a frontend change still runs the old JS, so `GET /api/build` returns `server.build_id()` (hash of static file names + mtimes + sizes, computed per request) and `common.js` `Build.check()` compares it with the id it first saw, on every WebSocket (re)connect and whenever the tab becomes visible: it reloads when `Build.canReload()` (the editor says no while there are unsaved edits, undo/redo history, a recording, a run or anchor mode), otherwise it shows a sticky notice whose 「刷新」 runs `Build.beforeReload()` (`ensureSaved`) first. `uvicorn[standard]` is required for WebSockets: TestClient works without it, so the tests won't catch its absence.
- **studio frontend conventions**: `common.js` provides the icon set (`icon(name)` / `<i data-icon>`), `Theme` (preference `dark` (default) / `light` / `system` in localStorage `cw.theme`, applied as `data-theme` on `<html>`; each page has an inline `<head>` script that sets it before first paint), `api()`, `toast()`, `confirmClick()` (two-click confirm; never use `confirm()`) and `connectEvents()`. `tour.js` is the onboarding tour, which auto-starts once per page (`cw.tour.editor` / `cw.tour.audit` in localStorage); update its steps when you move or rename UI. `style.css` uses design tokens only. The canvas path animation redraws at most `FLOW_FPS` (30) times a second and stops when the browser isn't focused or there was no input for `FLOW_IDLE_MS` (1 min); any pointer/key/wheel/focus wakes it. Components reference `var(--…)` and dark mode overrides the tokens, so never hard-code colors. Avoid generic class names that collide with step types (`.scroll` was one).
- **Drafts**: `POST /api/scripts` creates a *draft* under `user_data/drafts/` with an id prefixed `_draft/`. Every route works on drafts. `POST …/commit` (the 保存 button) moves the draft into `user_data/platforms/` via `state.relocate_macro`. The UI has **no save button**: `open()` commits a draft right away (so a new macro lands in the library), and every `mutate` / undo / redo calls `scheduleSave()` (600 ms debounce → `ensureSaved()` → `writeBack()`; edits made while a save is in flight stay on the page and are saved again). The picker subtitle shows 「正在保存…」 / 「已自动保存」. Pages/anchors are **per macro** (`<stem>.pages.yaml` + `<stem>.anchors/` next to the yaml; `default_pages_ref`). The macro list must skip `*.pages.yaml`. New macro and pack import live in the picker footer (`#mp`, searchable, Ctrl/⌘+K).
- **Platform packs (`.cwpack`)**: a zip of one `user_data/platforms/<platform>/` dir plus `manifest.json`. `adapters/pack.py` is format only: `export_pack(screenshots=True)` includes the recording screenshots (window references, step shots) so importers can see where each step acts; with `[studio] pack_screenshots = false` (settings 「导出时带上截图」) it skips those files and strips the fields. The route sets `X-Pack-Screenshots` and the UI toasts a privacy reminder; `unpack` validates the whole pack in memory first (yaml/json/png only, no zip-slip, macros/pages must validate, refs can't point outside) and writes nothing on failure (`PackError`, Chinese message). `Studio.import_pack` unpacks into a `user_data/.import-*` temp dir, then moves each macro with `unique_stem` + `relocate_macro` (same path as saving a draft); platform-level files are copied only if missing. Upload is the raw request body (no `python-multipart`). UI: per-platform 「导出」 in the picker groups, 「导入平台包」 in the picker footer, or drop a file anywhere on the page. No confirmation dialogs anywhere; name collisions get `-N` on both the file stem and the display name (`state.renamed`, also used by create and commit).
- **Multi-window**: `Step.win` names a key in `Script.windows` (None = `Script.window`, the main window). The recorder resolves the window per event via `ScreenIO.window_geometry_at` (mouse) and `foreground` (keys). It never uses rect tests, because windows overlap. It ignores the studio browser window (`recorder.is_studio_title`: page titles end with ` · 赛博打工人`, legacy `cyber-worker studio` also matches; keep these in sync if you rename the UI) and matches windows by app + `stable_title`. A window seen again takes this recording's size (`_resolve_locked` updates `width`/`height`/`scale`): keeping the old size once made the runner resize a 680-wide chat to 930 and miss every target. On stop, windows no step or anchor uses are dropped. It records **only the target program** (`RecordingBuilder.apps`: the main window's app plus apps already in `Script.windows`, `.exe` / case ignored); events in any other program (a terminal, browser, game launcher…) are dropped, so a recording left running can't pull them in. The runner calibrates when the window changes and waits up to `WINDOW_WAIT` for a window opened by the previous step. Frames, auto anchors (`Anchor.win`), the latest frame and canvas markers are all per window. Each window has its own reference image: main = `Script.reference` (`<stem>.png`), others = `Window.reference` (`<stem>.refs/<key>.png`, via `anchors.save_reference` / `Script.reference_for`). Recording stop saves each window's first step frame (else its first sampled frame) as its reference (append mode keeps existing ones) and its last frame as its latest (`Studio.latest[id][key]`, `set_latest`); `capture?win=` fills a missing reference. The canvas (and framing on 「录制画面」) uses `Script.shown_reference(key)`: the window's first step shot, else its stored reference, so old macros whose stored reference was a bogus screen grab still look right. `describe()` returns `frames.reference` / `frames.latest` as window key (`main` / `wN`) → frame. In the editor `S.win` is the window on the canvas: `select()` switches it to the step's window, `#win-seg` switches it by hand (lists only windows that steps use, plus the one shown; hidden below two), and anchors/targets/capture send `win`. `relocate_macro` / `_remove_macro_files` move/delete `<stem>.refs/`; Each step also has `Step.shot` (`<stem>.shots/<id>.png`): the window before the action, captured at mouse press (`_grab_target` → `press_frames`) or when a type/key/scroll step starts (`RecordingBuilder.on_step` → `step_frames`). `record._save_shots` saves a new file only if `vision/detect.frame_changed` against the last saved shot of that window, otherwise the step reuses that path. `describe()` returns `shots`; selecting a step with a shot shows it as 「参考图」 (`stepShot` / `frameParams` → anchors/targets with `frame: "step"`). Selecting a step keeps the frame kind the user chose (it used to force 「录制画面」, so a fresh capture seemed to vanish on the next click). Capturing while on 「录制画面」 replaces that frame (`capture?replace=true&step_id=`, `anchors.replace_frame`): the step's shot and every step sharing it, or without a step the window's shown reference; it writes a new file (`-N` suffix; main reference goes to `<stem>.refs/main-N.png`) and the UI pushes the old script onto undo so Ctrl+Z restores the old path. `_remove_macro_files` also deletes `<stem>.png`, which is orphaned once the main reference was replaced. Delays are not steps: `Script.renumber()` numbers actions `s01, s02…` and waits `d01, d02…` (applied on save, at record stop with `auto_send` remapped, and when `describe()` opens an old macro), and the UI's `actionNo()` shows the same 「第 N 步」 in the list (delay rows are unnumbered, dimmer `.step.idle`), header (「4 步 · 6.3 秒」), canvas markers, panel title, run log and audit. A selected `wait` shows no frame (it touches no window); a selected `wait_page` switches to its page's anchor window and the canvas highlights that page's anchors. Shots move/delete with the macro like refs. Real QQ needs a **double-click** in its narrow main window to open a chat.
- **Run effects**: the runner's io is `macro/io/effects.EffectsIO` wrapping the platform io (recording, capture and studio use the bare `App.io`). It forwards every call and tells an `Overlay` what to draw: click / double (two clicks of the same button within `DOUBLE_SEC`) / press+release (long press vs drag, path sampled from the cursor each frame) / scroll / key (`pretty_combo`) / type / hover (the runner calls `io.effect("hover")` if present). Overlay errors are swallowed. A double needs the same button within `DOUBLE_SEC` **and** within `DOUBLE_SLOP` points, so two adjacent single-click steps don't show 「双击」. `EffectBoard` turns events into time-based sprites (premultiplied BGRA, cv2 AA shapes, PIL text pills) and is platform-free and unit-tested. `win_overlay.WinOverlay` draws each sprite in its own layered, click-through, no-activate, topmost, untitled window on a dedicated thread, positioned from `GetCursorPos`; `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` keeps them out of screen grabs, and it must be set **before** adding `WS_EX_LAYERED` (on a layered window it fails with error 8). macOS uses `NullOverlay` (TODO). `[executor] show_effects` (settings 「显示操作效果」) toggles `App.effects.enabled` live. `python -m cyber_worker.macro.io.win_overlay` plays a demo (effects and sounds) without touching input.
- **Run sounds**: `EffectsIO.effect` also calls `Sound.play(kind, **kw)` when `sound_enabled` (`[executor] play_sounds`, settings 「操作音效」, live via `App.effects.sound_enabled`). `macro/io/sounds.py` is platform-free: `bank()` loads recordings from `macro/io/sound_assets/` (typing = `key-blue-*.wav`, 8 Cherry MX Blue presses; mouse = `mouse-press.wav` + `mouse-release.wav`, a click is press + release after `CLICK_GAP`, right/middle = `_pitch(click, 0.85)`), falling back to synthesized `_blue` / `_mouse` if a file is missing; it synthesizes the rest with numpy (scroll tick, Enter = `_big_key`, a mechanical-keyboard Enter; band-limited noise via diff + triangular smoothing, because raw noise was mostly >8 kHz hiss). `cues()` maps events to sounds (double = the second click's sound; Enter / newline = `enter`; Backspace / 清空输入框 = soft key; hover silent; scroll ticks capped at `MAX_SCROLL_TICKS`), and `Mixer` sums overlapping voices with tanh soft-limiting. `win_sound.WinSound` streams `Mixer` output through winmm `waveOut` (4 × 512-sample blocks) on its own thread, opening the device on the first sound and closing it after `IDLE_CLOSE`. `PlaySound` can't overlap sounds (a new one cuts the old one), which is why it isn't used here; the start chime still uses `PlaySound` and is a separate stream. macOS uses `NullSound` (TODO).
- **IME**: low-level hooks only see raw keys. `ScreenIO.ime_active` (Windows: `WM_IME_CONTROL` to the IME window) flags `TypeText.typed_with_ime`. The runner refuses such steps until the user edits the text, which clears the flag in the UI. Not implemented on macOS yet.
- **Global hotkeys (studio)**: `macro/io/hotkeys.HotkeyManager` owns the record toggle (`[studio] record_hotkey`, default `alt+r`), dry run (`[studio] dry_run_hotkey`, default `alt+t`; not `alt+d`, which is the browser address bar) and panic (`[executor] panic_hotkey`). **Real execution deliberately has no global hotkey** (it sends; a slip in any window must not post anything): in the page only, `Ctrl/⌘+Enter` clicks 「执行」, so it needs two presses like the button's `confirmClick`. Dry run → `routes/run.hotkey_dry_run`: runs `Studio.current_id` with `Studio.current_vars` (the UI sends its variables with `POST /api/current`) and refuses (toast) while recording, while `executor.busy` (so a double press runs once; `busy` is a pending-job counter, no gap between dequeue and run), or with missing variables. If the page reported unsaved edits (`POST /api/current` carries `dirty` + a per-tab `page` id, re-sent whenever `S.dirty` flips, withdrawn by a `pagehide` beacon), it doesn't run the stale file: it publishes `dry_run_request` and that tab runs `run(true)` (write back, then run, same as the button; `runStarting` stops a double press from running twice). Otherwise it runs the saved file. `create_app` → `routes/hotkeys.bind` registers them. Record → `routes/record.toggle_recording` on the macro the UI last reported via `POST /api/current`; panic → executor. Backends: Windows `WinHotkeys` (system `RegisterHotKey` on a dedicated message-loop thread, so it is exclusive and `available()` probes whether another program holds a key); macOS `PynputBackend` (passive listener, can't detect other apps). `check_combo` rejects reserved / duplicate / modifier-less combos. `apply()` falls back through `CANDIDATES` when the configured key is unusable and records `notes` (shown as toasts and in the terminal). Always read keys via `hotkeys.effective(name)`, never from config, because the effective key may differ. The hotkeys section of the settings dialog uses `/api/hotkeys` (check / PUT writes `config.toml` via `config.save_value` / suspend+resume while capturing). Tests pass `FakeHotkeys` and a tmp `config_path`, so they never write the repo config. The recorder drops all effective combos — record, dry run, panic (`ignore_combos`). Start and stop share `start_recording` / `stop_recording`; the stop result is pushed as `record_done`, which the UI dedupes with `rec_id`. `rec_id` is a uuid, never a counter: a counter restarts with studio while an open page remembers old values, so it silently dropped results and the screen showed stale steps (later "suddenly" revealing several appended recordings). On every WebSocket (re)connect the editor reloads the open macro unless it has unsaved edits. Recording **replaces** existing steps by default (`[studio] record_append`; the record ▾ menu `#record-menu` shows 「录制延迟」 as a switch and 「重新录制时：替换旧步骤 / 接在后面」 as a segmented choice `#opt-mode`, kept in sync via the `settings` event; footer links to 设置 › 录制与执行); the result carries `replaced`, the UI pushes the old script onto the undo stack, and new target images use `save_target_crop(keep_existing=True)` so `s01.png` of the replaced step survives for undo (`s01-2.png`). Both hold `Studio.record_lock` (non-blocking; a second call gets 409). Stopping takes seconds, so it chimes (`ScreenIO.chime`) and publishes `record_state` with `stopping: true` right away (UI: 「正在保存录制…」); start chimes too. `toggle_recording` silently ignores a press while the lock is held and for `RESTART_COOLDOWN` (1.5 s) after a stop, because users press again when they see no reaction (that once started a second recording that captured 20 minutes of unrelated work). `listen(held=ScreenIO.held_modifiers)` seeds the modifier set after the hooks are up, so the still-held Alt of the start hotkey makes the R count as `alt+r` (ignored) instead of typing `r`; macOS `held_modifiers` is a TODO. `pynput_input.HotkeyListener` (used by `listen_hotkeys` off-macOS) ignores injected input, so tests of it need `include_injected=True`; `RegisterHotKey`, by contrast, does fire on injected keys.
- **Settings**: the gear (⚙) opens `static/settings.js`, a dialog with sections on the left (通用 / 快捷键 / 录制与执行 / 关于) and settings on the right. Every change applies immediately with no save button. Non-hotkey settings go through `GET/PATCH /api/settings` (`routes/settings.py`). They are persisted to `config.toml` via `save_value`, applied live (`Studio.run_idle_sec` / `record_delays` / `record_append`, executor `pause_on_user_input` / `resume_after_idle_sec`), and broadcast as a `settings` event. `config.toml` is the source of truth: on load the page adopts the server's `theme`. The UI is **Chinese only**: the user explicitly does not want an English UI or a language switch. Don't add i18n.
- **Gestures**: `Click` has `count` (double-click), `hold` (long-press seconds), `button` (left/right/middle) and `modifiers`. There is also `Drag` (x,y → x2,y2, duration), `Key.times` (repeat count), `Scroll.dx` (horizontal) and `Hover` (x, y, seconds, optional `target`; the runner moves there and waits). Hovers are recorded **only when something changed**: `RecordingBuilder.on_move` just stores `pointer` (jitter within `HOVER_SLOP` keeps the same rest; real hands always jitter, and treating that as a move once made every hover vanish); `routes/record._watch_hover` (background thread) waits for a `REST_SEC` rest in a target-program window, captures it and `list_windows()`, then every `HOVER_CHECK` while still resting (up to `HOVER_MAX`, from `HOVER_MIN` on) checks for a new target-app window or `frame_changed`; after the pointer leaves it only checks for new windows (the hover highlight vanishing changes the frame), and leaving before `HOVER_MIN` (a pause on the way) is discarded; any click/key/scroll meanwhile (`builder.events`) discards it. `finish()` at stop inserts hovers by time (splitting a delay row) and renumbers (`press_of` / `step_frames` remapped). Rests that start right after a click near the same spot are not hovers (`RecordingBuilder.settling_after_click`, `CLICK_SETTLE_SEC` / `CLICK_SETTLE_DIST`): a chat window opening slowly after a double-click once got recorded as a hover popup. A window the recording typed into (type/key steps) is never a popup, which also clears a flag inherited from an older same-title window (a profile card titled like the chat). Windows that popped up after a hover get `Window.popup`, and the runner uses `ScreenIO.locate_window` (no activate, no resize) for them. The recorder distinguishes them from mouse down/up (`DRAG_SLOP`, `LONG_PRESS_SEC`, `DOUBLE_CLICK_SEC`), merges auto-repeat and wheel bursts, and accumulates fractional touchpad deltas. Listener callbacks are wrapped so an exception can't kill pynput's thread. Everything held down is released in `finally`. `listen(include_injected=True)` exists only for record→replay self-tests.
- **Brand**: the UI shows 「赛博打工人」 + a `Studio` tag (`.wordmark` / `.brand-tag`). `cyber-worker` stays as the repo, package and CLI name only.
- **Logo**: the 🤖 character itself, drawn by the system emoji font. It appears in `.logo-mark`, the favicon (`<text>🤖</text>` inside an SVG data URI), `docs/assets/logo.svg` and the README titles. The user wants exactly what Windows/GitHub show. Don't replace it with a traced SVG: platform emoji artwork such as Segoe UI Emoji is copyrighted, and referencing the character is not.
- **UX rule from the user: if the system can work something out, don't make the user type it.** The first-run path is a single button: click the target window (`POST /api/windows/pick` → `App.wait_click` + `ScreenIO.window_at`), which creates the macro and starts recording. New macros are created with one click, either on a window or on a `list_windows()` entry (minimized windows included); the form only appears under 「自定义」. `state.stable_title` strips changing title parts (QQ 「…等N个会话」, unread counters) so `Window.title` still matches later. While recording, `routes/record.py` samples frames. On stop, `vision/auto_anchor.pick_stable_region` picks a region that is unchanged across the frames, textured, unique in the frame, away from clicks and caption buttons, and biased toward the top. It becomes `页面1` and is assigned to the type/send steps. If an existing page whose anchors are all in that window matches the window's last frame (`match_page`), `_auto_anchor` reuses it instead (result `reused`), so re-recording doesn't pile up `页面2`, `页面3`. In replace mode, `_drop_unused_pages` then deletes pages (and their anchor images) that no step's `expected_page` or `WaitPage.page` uses (`dropped_pages`). `_auto_anchor` puts each window's step shots (`_step_frames_by_win`, taken before renumbering) ahead of the sampled frames, and `pick_stable_region` first runs `drop_odd_frames` (wrong size, or more than half the pixels differ from the median frame): one half-drawn or screen-grab frame once marked the whole window as changed, so nothing was picked and the type step was silently left without a page. Steps still without a page come back as `auto_anchor.missing`; the UI selects the first one and toasts what to do. Send-guessing stays on for clicks too: a false positive only stops a dry run early, while a miss would make a dry run really send. Names are free text (Chinese OK); file stems and platform dirs are derived (`state.safe_stem` / `platform_slug`) and collisions get a `-2` suffix. Anchor names default to `页面N`, and creating an anchor auto-fills `expected_page` on type/send steps that lack one **in the same window** (`Anchor.win` vs `Step.win`; a main-window anchor checked against a chat window never matches). `problems()` takes page → anchor windows and flags a step whose page was captured in another window. **Every problem says what to do** (the user couldn't act on 「必须指定所在页面」 alone): the editor's `localProblems()` returns `{text, hint, fixes}` and the step panel renders the hint plus fix buttons (`fixProblem`): 「自动选一个」 (`POST …/auto-page` → `anchors.auto_page`: reuse a same-window page that matches the step's shot, else pick a region from that window's shots / reference / latest frame and assign it; a `WaitPage` gets `page`), 「我自己框」 (switch to the step's window, anchor mode, `S.anchorFor` gives the new page to that step), 移回目标中心, 改文字, 设为变量, 选页面. Several type/key steps after the same click draw their focus squares side by side (`slot`), and the selected marker is drawn last. `{变量}` used in text is auto-declared (variable names may be Unicode). While recording, every mouse press calls `RecordingBuilder.on_press`. `routes/record._grab_target` captures the window in a background thread, because a slow low-level hook gets unhooked by Windows. `vision/template.pick_target` then keeps a crop around the click only if it is textured and unique in the window. On stop, those crops become `Click.target` (`<stem>.targets/<step>.png`, moved and deleted with the macro by `state.relocate_macro` / `_remove_macro_files`). Clicks on blank or flat areas stay fixed-coordinate. On recording stop, `recorder.guess_send_step` marks the click/enter right after the last typing step as `sends` (only when the macro has no send step yet). Don't add browser `pattern=` validation on free-text fields: JS `\w` is ASCII-only and rejects Chinese.
- **Audit retention**: there is no per-entry delete (the log is the record of what the program did on the user's behalf). Day views load every row of that day (`entries(limit=None)`, so the report isn't computed on a truncated list) and the date list covers `keep_days + 1` days. `[audit] keep_days` (default 30, settings 「审计记录保留」) is applied by `App.prune_audit` at studio start and CLI `run` (DB rows via `delete_before`, screenshot day dirs via `ScreenshotStorage.cleanup`); changing the setting does not delete anything until the next start. The audit page's trash button next to refresh clears the selected day (`DELETE /api/audit/days/{day}` → `delete_day` + `storage.remove_day`, two-click `confirmClick`). Audit screenshots (`ScreenshotStorage.save`) are lossless WebP (`write_image` picks the codec by suffix; about 60% smaller than PNG, pixel-identical); `/api/file` serves `.png` and `.webp` only. Macro images (anchors, targets, refs, shots) stay PNG. Keys on the audit page: ↑/↓ switch runs, ←/→ switch steps within the run, 1/2 mark. A failed/aborted step keeps the runner's original reason and gets an 「怎么修」 box (`audit.advise`, matched on the raw detail) with a 「去修改」 link to `/?macro=…&step=…` when the fix is in the macro; reasons that need no edit (you touched the mouse, window not open) say so instead. The review bar's own 「去修改」 (shown for runs marked 要修) is hidden while the advice box has one, so there is never a second button; it stays for reasons without advice and for runs that didn't fail. A run whose failure needs no edit (`noFix`: advice with `edit: false`) shows only 「看过了」: no 「有问题，要修」 (key 2 ignored) and no 「去修改」, even if it was marked 要修 earlier (看过了 clears that mark). Successful runs keep 「有问题，要修」 on purpose: only the user can see from the screenshot that a "successful" click hit the wrong chat. Add a case there whenever the runner gains a new abort reason.
- **Local-only guard**: `studio/guard.LocalOnly` (ASGI middleware, added last in `create_app`) rejects any HTTP request or WebSocket whose `Host` is not `127.0.0.1` / `localhost` / `::1` (DNS rebinding) or whose `Origin`, when present, isn't one of those (other web pages; WebSockets always send Origin). Tests use `TestClient(..., base_url="http://127.0.0.1:9999")` and the absolute `WS = "ws://127.0.0.1:9999/ws"` because Starlette's `websocket_connect` ignores `base_url`.
- **Retired pages and garbage collection**: replace-recording moves pages no step uses from `PageBook.pages` into `PageBook.retired` (+ `retired_at`) instead of deleting them; anchor images stay. `PUT …/detail` calls `anchors.restore_pages`, so undoing a recording brings back the pages its steps use. `_auto_anchor` and `add_anchor` never reuse a retired name (`add_anchor` discards a retired page of the same name). At studio start `Studio.collect_garbage` also empties `user_data/frames/` (latest frames are tracked only in memory, so after a restart nothing reads them) and removes platform dirs that contain no files; per macro, `state.collect_garbage(path)` purges retired pages older than `GARBAGE_AGE` (3 days) and deletes `.shots/`, `.targets/`, `.refs/`, own `.anchors/` PNGs and `<stem>.png` that nothing references and that are older than that, so undo still works within a session. `relocate_macro` and pack validation also cover retired anchors.
- **Interruptible waits**: the runner sleeps through `Wait` and `Hover` in `TICK` (0.1 s) slices via `_pause`. A delay checks only `Gate.check_cancel`, so panic is immediate and a mouse nudge doesn't abort the run (the next step's `gate.wait()` pauses instead). A hover uses `gate.check`, because moving the mouse would dismiss the popup anyway.
- For manual UI checks without touching the real screen, run a throwaway script that builds an `App` with `FakeIO` and calls `studio.server.create_app` (keep it out of the repo).

### Comment / post workflow

`engine/workflow/comment.py` drives: watch hit → ① extract (adapter) + decide (rules: relationship lists, frequency caps, random threshold) → ② LLM draft (minimum context) → ③ pending queue → ④ execute via executor → ⑤ record (audit gets the screenshot and log; feedback gets the final text, diff and choice). The states are `pending → approved / edited / rejected → executed / failed`, and confirmation can take hours. After approval, the workflow triggers execution; **studio never calls macro directly.** Posting uses the same queue but is triggered by `policy_post` timing, not by the monitor. Feedback signals: an approval reinforces the style, an edit's diff is the strongest signal, and a rejection is routed by its reason ("shouldn't comment" → decision, "not like me" → phrasing).

## Constraints

- **Pending queue by default**: comments and posts are never sent without confirmation unless the user enables `*_auto_send` in `config.toml`.
- **Screen-level only**: no CDP, Selenium or DOM automation, including on web platforms.
- **Out of scope** (stated in the README): bulk registration, engagement farming, spam, opinion manipulation, CAPTCHA bypass.
- **Secrets and data**: `.env` holds only the LLM API key, and no platform credentials or cookies are stored. `user_data/`, `.env`, `config.toml` and `persona.md` are gitignored; commit only the `*.example.*` templates.
- **Privacy**: send the LLM only the minimum context, and never extract content from people on the `never_comment` list. Reference screenshots and test fixtures must come from test accounts or be redacted (no real friends' avatars, names or content), and are stored via Git LFS.
- **Detection tests** (`tests/fixtures/anomaly/`, `detect/`) use real screenshots grouped TP/FP/TN/FN. False positives (an action that failed but was judged a success) are the most dangerous case, so don't regress them.
