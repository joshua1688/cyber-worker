# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

Implemented so far: the `macro/` minimal loop (schema, runner, executor, recorder, act, vision/fingerprint, anchors, screenshot storage, audit incl. reviewer/reporter) + platform pack export / import (`adapters/pack.py`, `.cwpack`) + `infra/sqlite` audit store + `studio/` (macro editor at `/`, audit page at `/audit`) + CLI `studio` / `record` / `anchor` / `run`. Everything else in the README tree is still to be built, in roadmap order. Usage: `docs/studio.md`, `docs/macro.md`. **`README.zh-CN.md` is the source of truth**; `README.md` is its English translation. When the design changes, update the Chinese README first, then sync the English one and this file. The "目录结构 / Project structure" section is the target layout, so build toward it rather than inventing a different structure.

## Commands

```bash
uv sync                                   # install dependencies (Python 3.11+)
uv run cyber-worker studio                # web editor + audit page on :9999 (macOS / Windows)
uv run cyber-worker record OUT.yaml --app WeChat --size 1200x900
uv run cyber-worker anchor SCRIPT.yaml PAGE --region x,y,w,h
uv run cyber-worker run SCRIPT.yaml [--dry-run] [--var name=value]
uv run pytest                             # run tests
uv run pytest tests/macro/test_runner.py::test_name   # single test
```

Supported platforms are **macOS and Windows** (`bootstrap._platform_io` picks one; Linux raises). Shared mouse/keyboard code lives in `macro/io/pynput_input.py`. `macos.py` handles windows and capture via `screencapture` + `osascript`. `windows.py` uses Win32 via ctypes + Pillow. `capture` uses `PrintWindow(PW_RENDERFULLCONTENT)` on `WindowGeometry.handle` (the window's own pixels, correct even when another window covers it), cropped to the DWM frame; it falls back to a screen grab when there is no handle, the result is all black, or the size is off. A covered window captured as a screen region once produced a bogus hover whose step image showed the studio page. It is per-monitor DPI aware, so pynput coordinates are physical pixels and `input_factor` converts them to points. It types with `SendInput(KEYEVENTF_UNICODE)` so the Chinese IME can't swallow letters, and uses an Alt-press + `AttachThreadInput` trick to get past foreground-lock. `Window.title` (optional) picks one window when an app has several. Everything else depends on the `ScreenIO` / `ActivityMonitor` protocols in `macro/io/base.py`, and the tests use `tests/fakes.py` (FakeIO records calls; `typed()` replays backspaces and `clear`). `tests/helpers.py` builds synthetic page fingerprints. Test files import `fakes` / `helpers` as top-level modules (via `tests/conftest.py`), so don't add `__init__.py` under `tests/`.

## Architecture

Code lives under `src/cyber_worker/`. **Dependency direction:** `engine` depends only on `engine/ports/`; `adapters` and `infra` implement those ports; `macro` is platform-agnostic; `bootstrap.py` is the single wiring point, called by both `cli.py` and studio. Don't construct dependencies anywhere else.

- **engine/** decides *what*. Ports: `PlatformPort` (watch / extract / browse_feed / like / comment / publish), `ReviewQueue`, `MemoryStore`, `LLM`, `Clock` (fake clock to fast-forward 24h in tests). `monitor.py` polls watch regions; `decision/` holds rule-based policies; `tone/` drafts with the LLM and learns from feedback; `workflow/` holds the long-running state machines.
- **macro/** decides *how*. `executor.py` is the **only** path to the mouse and keyboard: every action (studio recording/runs, engine actions) is queued and mutually exclusive, pauses on user input, and a panic hotkey clears the queue. `runner.py` calibrates the window (coordinates are window-relative, with recorded window size and Retina scale), verifies `expected_page` fingerprints **before any type/send step**. It polls up to `PAGE_WAIT` (5 s) for the page to appear and only then aborts, flagging the action as suspicious. It finds `Click.target` images before clicking (`locator/icon.locate_click`, via `vision/template.find_all`; the nearest match wins). The click offset relative to the target is kept, the runner waits up to `target.timeout` (if the best match is only `NEAR` (≥ 0.6), e.g. a button captured with its hover highlight, it first moves the pointer onto that spot once so the highlight appears, then keeps matching), and if the target never shows it aborts and **never falls back to the old coordinates**. It runs `WaitPage` steps (wait for a page, then continue). It also performs `Click.count == 2` as a real double-click (one move, then two clicks 60–120 ms apart in place; separate click steps are never fast enough for the OS to treat them as a double-click, and the recorder merges clicks at the same spot within 0.5 s into one), clears the input field before typing unless `clear_first: false` (otherwise leftovers from a dry/interrupted run would get sent), screenshots after every step, and supports `dry_run` (everything except the final send). Image algorithms live in `vision/` (ocr, template, fingerprint, detect, anomaly); `locator/` only decides where to click. `audit/` is pure logic, with no HTTP.
- **adapters/** decides *where*, using **declarative platform packs**. One generic `screen_adapter.py` reads each `adapters/<platform>/` pack: `platform.yaml` (capability → macro, extraction regions + OCR, window size), `pages.yaml` (fingerprints, watch regions), `templates/*.yaml` (recorded macros), `reference/`. Adding a platform means adding a pack, not code. Per-platform Python (`hooks.py`) is optional and only for complex extraction. `loader.py` overlays `user_data/platforms/` on top of the built-ins (same-name files win).
- **infra/** holds the concrete port implementations: SQLite (`state.db`: pending queue, memory, audit) and the LLM client (cloud or local).
- **studio/** is FastAPI + WebSocket with a vanilla HTML/JS/Canvas frontend: **web only, no frontend framework, no desktop UI framework** (no Electron/Tauri/PyQt/Tkinter). The editor layout: left "添加" palette, middle step list with record ▾ / undo / redo / save, delays as their own rows. Routes only display and submit; business logic belongs in engine/macro. `studio/state.py` owns all filesystem access (scripts live in `user_data/platforms/<platform>/templates/*.yaml`, path-traversal checked). Worker threads publish to the browser through `Hub.publish` (thread-safe). A run publishes `run_state` events in the order `queued` (waiting for the user to stop touching mouse/keyboard), then `running` (published from inside the job), then `done`. The UI must always show what it's waiting for, with a cancel button; never leave a bare disabled button. Events can be lost while the WebSocket reconnects, so the editor re-syncs from `GET /api/status` on reconnect and every 3 s while a run is active. Static files are served `no-cache`. `uvicorn[standard]` is required for WebSockets: TestClient works without it, so the tests won't catch its absence.
- **studio frontend conventions**: `common.js` provides the icon set (`icon(name)` / `<i data-icon>`), `Theme` (preference `dark` (default) / `light` / `system` in localStorage `cw.theme`, applied as `data-theme` on `<html>`; each page has an inline `<head>` script that sets it before first paint), `api()`, `toast()`, `confirmClick()` (two-click confirm; never use `confirm()`) and `connectEvents()`. `tour.js` is the onboarding tour, which auto-starts once per page (`cw.tour.editor` / `cw.tour.audit` in localStorage); update its steps when you move or rename UI. `style.css` uses design tokens only. Components reference `var(--…)` and dark mode overrides the tokens, so never hard-code colors. Avoid generic class names that collide with step types (`.scroll` was one).
- **Drafts**: `POST /api/scripts` creates a *draft* under `user_data/drafts/` with an id prefixed `_draft/`. Every route works on drafts. `POST …/commit` (the 保存 button) moves the draft into `user_data/platforms/` via `state.relocate_macro`. In the UI, `ensureSaved()` only writes back, while `save()` also commits drafts. Pages/anchors are **per macro** (`<stem>.pages.yaml` + `<stem>.anchors/` next to the yaml; `default_pages_ref`). The macro list must skip `*.pages.yaml`. New / 保存 / 删除 sit together next to the custom macro picker (`#mp`, searchable, Ctrl/⌘+K).
- **Platform packs (`.cwpack`)**: a zip of one `user_data/platforms/<platform>/` dir plus `manifest.json`. `adapters/pack.py` is format only: `export_pack(screenshots=True)` includes the recording screenshots (window references, step shots) so importers can see where each step acts; with `[studio] pack_screenshots = false` (settings 「导出时带上截图」) it skips those files and strips the fields. The route sets `X-Pack-Screenshots` and the UI toasts a privacy reminder; `unpack` validates the whole pack in memory first (yaml/json/png only, no zip-slip, macros/pages must validate, refs can't point outside) and writes nothing on failure (`PackError`, Chinese message). `Studio.import_pack` unpacks into a `user_data/.import-*` temp dir, then moves each macro with `unique_stem` + `relocate_macro` (same path as saving a draft); platform-level files are copied only if missing. Upload is the raw request body (no `python-multipart`). UI: per-platform 「导出」 in the picker groups, 「导入平台包」 in the picker footer, or drop a file anywhere on the page. No confirmation dialogs anywhere; name collisions get `-N` on both the file stem and the display name (`state.renamed`, also used by create and commit).
- **Multi-window**: `Step.win` names a key in `Script.windows` (None = `Script.window`, the main window). The recorder resolves the window per event via `ScreenIO.window_geometry_at` (mouse) and `foreground` (keys). It never uses rect tests, because windows overlap. It ignores the studio browser window (`recorder.is_studio_title`: page titles end with ` · 赛博打工人`, legacy `cyber-worker studio` also matches; keep these in sync if you rename the UI) and matches windows by app + `stable_title`. A window seen again takes this recording's size (`_resolve_locked` updates `width`/`height`/`scale`): keeping the old size once made the runner resize a 680-wide chat to 930 and miss every target. On stop, windows no step or anchor uses are dropped. It records **only the target program** (`RecordingBuilder.apps`: the main window's app plus apps already in `Script.windows`, `.exe` / case ignored); events in any other program (a terminal, browser, game launcher…) are dropped, so a recording left running can't pull them in. The runner calibrates when the window changes and waits up to `WINDOW_WAIT` for a window opened by the previous step. Frames, auto anchors (`Anchor.win`), the latest frame and canvas markers are all per window. Each window has its own reference image: main = `Script.reference` (`<stem>.png`), others = `Window.reference` (`<stem>.refs/<key>.png`, via `anchors.save_reference` / `Script.reference_for`). Recording stop saves each window's first frame as its reference (append mode keeps existing ones) and its last frame as its latest (`Studio.latest[id][key]`, `set_latest`); `capture?win=` fills a missing reference. `describe()` returns `frames.reference` / `frames.latest` as window key (`main` / `wN`) → frame. In the editor `S.win` is the window on the canvas: `select()` switches it to the step's window, `#win-seg` switches it by hand (lists only windows that steps use, plus the one shown; hidden below two), and anchors/targets/capture send `win`. `relocate_macro` / `_remove_macro_files` move/delete `<stem>.refs/`; Each step also has `Step.shot` (`<stem>.shots/<id>.png`): the window before the action, captured at mouse press (`_grab_target` → `press_frames`) or when a type/key/scroll step starts (`RecordingBuilder.on_step` → `step_frames`). `record._save_shots` saves a new file only if `vision/detect.frame_changed` against the last saved shot of that window, otherwise the step reuses that path. `describe()` returns `shots`; selecting a step with a shot shows it as 「参考图」 (`stepShot` / `frameParams` → anchors/targets with `frame: "step"`). A selected `wait` shows no frame (it touches no window); a selected `wait_page` switches to its page's anchor window and the canvas highlights that page's anchors. Shots move/delete with the macro like refs. Real QQ needs a **double-click** in its narrow main window to open a chat.
- **IME**: low-level hooks only see raw keys. `ScreenIO.ime_active` (Windows: `WM_IME_CONTROL` to the IME window) flags `TypeText.typed_with_ime`. The runner refuses such steps until the user edits the text, which clears the flag in the UI. Not implemented on macOS yet.
- **Global hotkeys (studio)**: `macro/io/hotkeys.HotkeyManager` owns the record toggle (`[studio] record_hotkey`, default `alt+r`), dry run (`[studio] dry_run_hotkey`, default `alt+t`; not `alt+d`, which is the browser address bar) and panic (`[executor] panic_hotkey`). **Real execution deliberately has no global hotkey** (it sends; a slip in any window must not post anything): in the page only, `Ctrl/⌘+Enter` clicks 「执行」, so it needs two presses like the button's `confirmClick`. Dry run → `routes/run.hotkey_dry_run`: runs `Studio.current_id` with `Studio.current_vars` (the UI sends its variables with `POST /api/current`), chimes, and refuses (toast) while recording, while `executor.busy` (so a double press runs once; `busy` is a pending-job counter, no gap between dequeue and run), or with missing variables. If the page reported unsaved edits (`POST /api/current` carries `dirty` + a per-tab `page` id, re-sent whenever `S.dirty` flips, withdrawn by a `pagehide` beacon), it doesn't run the stale file: it publishes `dry_run_request` and that tab runs `run(true)` (write back, then run, same as the button; `runStarting` stops a double press from running twice). Otherwise it runs the saved file. `create_app` → `routes/hotkeys.bind` registers them. Record → `routes/record.toggle_recording` on the macro the UI last reported via `POST /api/current`; panic → executor. Backends: Windows `WinHotkeys` (system `RegisterHotKey` on a dedicated message-loop thread, so it is exclusive and `available()` probes whether another program holds a key); macOS `PynputBackend` (passive listener, can't detect other apps). `check_combo` rejects reserved / duplicate / modifier-less combos. `apply()` falls back through `CANDIDATES` when the configured key is unusable and records `notes` (shown as toasts and in the terminal). Always read keys via `hotkeys.effective(name)`, never from config, because the effective key may differ. The hotkeys section of the settings dialog uses `/api/hotkeys` (check / PUT writes `config.toml` via `config.save_value` / suspend+resume while capturing). Tests pass `FakeHotkeys` and a tmp `config_path`, so they never write the repo config. The recorder drops all effective combos — record, dry run, panic (`ignore_combos`). Start and stop share `start_recording` / `stop_recording`; the stop result is pushed as `record_done`, which the UI dedupes with `rec_id`. `rec_id` is a uuid, never a counter: a counter restarts with studio while an open page remembers old values, so it silently dropped results and the screen showed stale steps (later "suddenly" revealing several appended recordings). On every WebSocket (re)connect the editor reloads the open macro unless it has unsaved edits. Recording **replaces** existing steps by default (`[studio] record_append`; the record ▾ menu `#record-menu` shows 「录制延迟」 as a switch and 「重新录制时：替换旧步骤 / 接在后面」 as a segmented choice `#opt-mode`, kept in sync via the `settings` event; footer links to 设置 › 录制与执行); the result carries `replaced`, the UI pushes the old script onto the undo stack, and new target images use `save_target_crop(keep_existing=True)` so `s01.png` of the replaced step survives for undo (`s01-2.png`). Both hold `Studio.record_lock` (non-blocking; a second call gets 409). Stopping takes seconds, so it chimes (`ScreenIO.chime`) and publishes `record_state` with `stopping: true` right away (UI: 「正在保存录制…」); start chimes too. `toggle_recording` silently ignores a press while the lock is held and for `RESTART_COOLDOWN` (1.5 s) after a stop, because users press again when they see no reaction (that once started a second recording that captured 20 minutes of unrelated work). `listen(held=ScreenIO.held_modifiers)` seeds the modifier set after the hooks are up, so the still-held Alt of the start hotkey makes the R count as `alt+r` (ignored) instead of typing `r`; macOS `held_modifiers` is a TODO. `pynput_input.HotkeyListener` (used by `listen_hotkeys` off-macOS) ignores injected input, so tests of it need `include_injected=True`; `RegisterHotKey`, by contrast, does fire on injected keys.
- **Settings**: the gear (⚙) opens `static/settings.js`, a dialog with sections on the left (通用 / 快捷键 / 录制与执行 / 关于) and settings on the right. Every change applies immediately with no save button. Non-hotkey settings go through `GET/PATCH /api/settings` (`routes/settings.py`). They are persisted to `config.toml` via `save_value`, applied live (`Studio.run_idle_sec` / `record_delays` / `record_append`, executor `pause_on_user_input` / `resume_after_idle_sec`), and broadcast as a `settings` event. `config.toml` is the source of truth: on load the page adopts the server's `theme`. The UI is **Chinese only**: the user explicitly does not want an English UI or a language switch. Don't add i18n.
- **Gestures**: `Click` has `count` (double-click), `hold` (long-press seconds), `button` (left/right/middle) and `modifiers`. There is also `Drag` (x,y → x2,y2, duration), `Key.times` (repeat count), `Scroll.dx` (horizontal) and `Hover` (x, y, seconds, optional `target`; the runner moves there and waits). Hovers are recorded **only when something changed**: `RecordingBuilder.on_move` just stores `pointer` (jitter within `HOVER_SLOP` keeps the same rest; real hands always jitter, and treating that as a move once made every hover vanish); `routes/record._watch_hover` (background thread) waits for a `REST_SEC` rest in a target-program window, captures it and `list_windows()`, then every `HOVER_CHECK` while still resting (up to `HOVER_MAX`, from `HOVER_MIN` on) checks for a new target-app window or `frame_changed`; after the pointer leaves it only checks for new windows (the hover highlight vanishing changes the frame), and leaving before `HOVER_MIN` (a pause on the way) is discarded; any click/key/scroll meanwhile (`builder.events`) discards it. `finish()` at stop inserts hovers by time (splitting a delay row) and renumbers (`press_of` / `step_frames` remapped). Windows that popped up after a hover get `Window.popup`, and the runner uses `ScreenIO.locate_window` (no activate, no resize) for them. The recorder distinguishes them from mouse down/up (`DRAG_SLOP`, `LONG_PRESS_SEC`, `DOUBLE_CLICK_SEC`), merges auto-repeat and wheel bursts, and accumulates fractional touchpad deltas. Listener callbacks are wrapped so an exception can't kill pynput's thread. Everything held down is released in `finally`. `listen(include_injected=True)` exists only for record→replay self-tests.
- **Brand**: the UI shows 「赛博打工人」 + a `Studio` tag (`.wordmark` / `.brand-tag`). `cyber-worker` stays as the repo, package and CLI name only.
- **Logo**: the 🤖 character itself, drawn by the system emoji font. It appears in `.logo-mark`, the favicon (`<text>🤖</text>` inside an SVG data URI), `docs/assets/logo.svg` and the README titles. The user wants exactly what Windows/GitHub show. Don't replace it with a traced SVG: platform emoji artwork such as Segoe UI Emoji is copyrighted, and referencing the character is not.
- **UX rule from the user: if the system can work something out, don't make the user type it.** The first-run path is a single button: click the target window (`POST /api/windows/pick` → `App.wait_click` + `ScreenIO.window_at`), which creates the macro and starts recording. New macros are created with one click, either on a window or on a `list_windows()` entry (minimized windows included); the form only appears under 「自定义」. `state.stable_title` strips changing title parts (QQ 「…等N个会话」, unread counters) so `Window.title` still matches later. While recording, `routes/record.py` samples frames. On stop, `vision/auto_anchor.pick_stable_region` picks a region that is unchanged across the frames, textured, unique in the frame, away from clicks and caption buttons, and biased toward the top. It becomes `页面1` and is assigned to the type/send steps. Names are free text (Chinese OK); file stems and platform dirs are derived (`state.safe_stem` / `platform_slug`) and collisions get a `-2` suffix. Anchor names default to `页面N`, and creating an anchor auto-fills `expected_page` on type/send steps that lack one **in the same window** (`Anchor.win` vs `Step.win`; a main-window anchor checked against a chat window never matches). `problems()` takes page → anchor windows and flags a step whose page was captured in another window. `{变量}` used in text is auto-declared (variable names may be Unicode). While recording, every mouse press calls `RecordingBuilder.on_press`. `routes/record._grab_target` captures the window in a background thread, because a slow low-level hook gets unhooked by Windows. `vision/template.pick_target` then keeps a crop around the click only if it is textured and unique in the window. On stop, those crops become `Click.target` (`<stem>.targets/<step>.png`, moved and deleted with the macro by `state.relocate_macro` / `_remove_macro_files`). Clicks on blank or flat areas stay fixed-coordinate. On recording stop, `recorder.guess_send_step` marks the click/enter right after the last typing step as `sends` (only when the macro has no send step yet). Don't add browser `pattern=` validation on free-text fields: JS `\w` is ASCII-only and rejects Chinese.
- For manual UI checks without touching the real screen, run a throwaway script that builds an `App` with `FakeIO` and calls `studio.server.create_app` (keep it out of the repo).

### Comment / post workflow

`engine/workflow/comment.py` drives: watch hit → ① extract (adapter) + decide (rules: relationship lists, frequency caps, random threshold) → ② LLM draft (minimum context) → ③ pending queue → ④ execute via executor → ⑤ record (audit gets the screenshot and log; feedback gets the final text, diff and choice). The states are `pending → approved / edited / rejected → executed / failed`, and confirmation can take hours. After approval, the workflow triggers execution; **studio never calls macro directly.** Posting uses the same queue but is triggered by `policy_post` timing, not by the monitor. Feedback signals: an approval reinforces the style, an edit's diff is the strongest signal, and a rejection is routed by its reason ("shouldn't comment" → decision, "not like me" → phrasing).

## Constraints

- **Pending queue by default**: comments and posts are never sent without confirmation unless the user enables `*_auto_send` in `config.toml`.
- **Screen-level only**: no CDP, Selenium or DOM automation, including on web platforms.
- **Out of scope** (stated in the README): bulk registration, engagement farming, spam, opinion manipulation, CAPTCHA bypass.
- **Secrets and data**: `.env` holds only the LLM API key, and no platform credentials or cookies are stored. `user_data/`, `.env`, `config.toml` and `persona.md` are gitignored; commit only the `*.example.*` templates.
- **Privacy**: send the LLM only the minimum context, and never extract content from people on the `never_comment` list. Reference screenshots and test fixtures must come from test accounts or be redacted (no real friends' avatars, names or content), and are stored via Git LFS.
- **Detection tests** (`tests/fixtures/anomaly/`, `detect/`) use real screenshots grouped TP/FP/TN/FN. False positives (an action that failed but was judged a success) are the most dangerous case, so don't regress them.
